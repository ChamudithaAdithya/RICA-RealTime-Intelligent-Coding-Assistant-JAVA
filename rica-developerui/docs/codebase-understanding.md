# RICA Codebase Understanding Guide

This guide explains how the RICA extension code is organised and what the important files, classes, methods, and test files do. It is written for defence preparation: if someone asks "where is this implemented?" or "what does this part do?", use this document as the map.

Use this guide together with `docs/codebase-method-index.md`, which is generated from the actual source files and lists every detected class/function/method declaration with line numbers.

RICA has three kinds of files:

- **Real TypeScript source**: `src/**/*.ts`. These are the files you should explain as the implementation.
- **Compiled JavaScript output**: many `src/**/*.js` and `src/**/*.js.map` files. These are generated by `npm run compile` from TypeScript and are used by VS Code at runtime because `package.json` points to `./src/extension.js`.
- **Hand-written JavaScript tests**: `src/test/**/*.test.js`. These are not generated. Mocha runs them directly.

## 1. Big Picture

RICA works in this order:

1. VS Code starts the extension from `src/extension.ts`.
2. The extension creates the parser, AST manager, violation manager, diagnostic reporter, file watcher, webviews, and optional AI coordinator.
3. Java files are discovered by `VscodeSourceProvider`.
4. Java files are parsed by `JavaParser`.
5. Parsed AST objects are stored by `ASTManager` and `ViolationManager`.
6. `ViolationManager` runs detector modules.
7. Detectors produce violations.
8. Violations are enriched with rule codes, evidence, documentation URLs, and optional fix suggestions.
9. `VscodeDiagnosticReporter` shows underlines in VS Code.
10. `ViolationsWebviewPanel` shows the Architecture Violations panel.
11. When a file changes, `FileWatcher` and `ImpactAnalyzer` decide what needs to be revalidated.

In one sentence:

> RICA is a VS Code extension that parses Java files into AST facts, builds project-level dependency context, runs deterministic architecture/design-pattern detectors, and shows findings through diagnostics, panels, and documentation links.

## 2. Source vs Generated Files

### TypeScript files

The `.ts` files are the source code you should understand and defend.

Example:

```text
src/controllerLayerDetector.ts
src/violationManager.ts
src/infrastructure/javaParser.ts
```

### Compiled JavaScript files

The matching `.js` files beside most `.ts` files are generated by TypeScript.

Example:

```text
src/controllerLayerDetector.ts  -> source
src/controllerLayerDetector.js  -> compiled output
src/controllerLayerDetector.js.map -> source map
```

They are important for packaging because `package.json` has:

```json
"main": "./src/extension.js"
```

That means VS Code runs the compiled JavaScript, but you should explain the TypeScript source.

### Test JavaScript files

The files under `src/test` are different. They are not generated. They are hand-written Mocha test files.

`.mocharc.js` says:

```js
spec: ['src/test/**/*.test.js']
```

So `npm test` runs the JavaScript test files directly.

## 3. Main Runtime Flow

### Full Project Analysis

The full scan starts at `src/extension.ts`.

```text
Command: Java AST: Analyze Full Project
extension.ts -> analyzeFullProject()
ASTManager -> analyzeFullProject()
JavaParser -> parse()
ViolationManager -> seedCache()
ViolationManager -> update()
Detectors -> analyze()
DiagnosticReporter -> report()
ViolationsWebviewPanel -> refresh()
```

What this means:

- The command comes from VS Code.
- `ASTManager` scans and parses every Java file.
- `ViolationManager` receives all ASTs.
- It runs service, controller, entity, API, graph, package, and design-pattern checks.
- Results appear as editor diagnostics and panel rows.

### Single File / Incremental Analysis

When a Java file is saved:

```text
FileWatcher -> onDocumentSaved()
ViolationManager -> onFileSaved()
JavaParserAdapter -> parse()
ImpactAnalyzer -> diffAstFacts()
ViolationManager -> selected detectors only
DiagnosticReporter -> report()
```

What this means:

- RICA does not blindly scan the whole project for every normal edit.
- It compares old AST facts with new AST facts.
- If imports changed, package and graph checks matter.
- If object creation changed, design-pattern checks related to construction may matter.
- If only irrelevant text changed, expensive analysis can be skipped.

### `src/infrastructure/javaParser.ts`

This is the largest file. It converts Java source code into RICA's AST facts.

Important responsibilities:

- Parse Java code using the `java-parser` library.
- Extract package and import information.
- Extract classes, interfaces, enums, annotations, fields, methods, constructors, parameters, method calls, object creation, local variables, persistence writes, accessed fields, and suppressions.
- Classify classes into layers such as controller, service, repository, entity, DTO, API resource, configuration, etc.
- Calculate metrics such as complexity, nesting, business-logic score, and line ranges.

Important method groups:

| Area | Example methods | Purpose |
|---|---|---|
| CST traversal | `parse`, `processClassDeclaration`, `processInterfaceDeclaration` | Walk Java parse tree and produce structured output. |
| Class extraction | `extractClassInfo`, `classifyClass`, `collectExternalDependencies` | Build `ClassInfo` objects with layer and dependency facts. |
| Method extraction | `extractMethods`, `extractMethod`, `analyzeMethodBody` | Extract method metadata, calls, complexity, variables, and body signals. |
| Constructor extraction | `extractDetailedConstructor`, `detectConstructorInjection`, `findAssignmentPatterns` | Detect constructor injection and constructor-created dependencies. |
| Call extraction | `extractMethodCallsFromBody`, `analyzeStatementForCalls`, `inferReceiverType` | Identify calls like `service.save()` and receiver type information. |
| Object creation | `extractObjectCreationsFromBody`, `extractObjectCreations` | Detect `new Something()` expressions for DI/pattern rules. |
| Annotations | `extractAnnotations`, `extractAnnotationElements`, `getAnnotationName` | Detect Spring and validation annotations. |
| Imports/package | `extractImports`, `parseImportNode`, `extractPackageInfoFromSource` | Build dependency and package facts. |
| Suppressions | `extractSuppressedLines` | Supports `rica-disable-next-line` style suppression. |
| Metrics | `extractComplexityMetrics`, `calculateBusinessLogicScore` | Supports business-logic and pattern heuristics. |

Defence explanation:

> `JavaParser` is not a full Java compiler. It extracts enough structural facts for fast editor-time architecture analysis. This is why the report describes RICA as AST-based static analysis rather than full semantic type checking.

### `src/dependencyGraph.ts`

This file builds and analyses the project dependency graph.

Important line ranges:

| Lines | What it does |
|---:|---|
| 1-4 | Imports AST/domain types. |
| 6-29 | Defines graph node, edge, edge-location, and graph violation shapes. |
| 43-305 | `ProjectDependencyGraph` stores nodes/edges and provides graph operations. |
| 47-81 | Add nodes and edges. Edge weights increase when the same relation repeats. |
| 83-141 | `resolveTypeFQN()` resolves simple class names to fully-qualified names. |
| 143-183 | Incoming/outgoing edges, fan-in, and fan-out. |
| 185-204 | Finds nodes by layer or simple class name. |
| 206-278 | Builds adjacency and finds strongly connected components with Tarjan's algorithm. |
| 280-305 | Reachability helpers for graph traversal. |
| 327+ | Builds and patches dependency graphs from AST files. |
| Later rule exports | Defines graph rules such as controller bypass, entity exposure, cycles, and cross-layer violations. |

Defence explanation:

> `dependencyGraph.ts` is how RICA moves beyond single-file linting. It gives RICA project-level knowledge of which classes depend on which other classes.

### `src/impactAnalyzer.ts`

This file decides what changed between an old AST and a new AST.

Main responsibilities:

- Compare AST fact groups such as imports, relationships, calls, fields, annotations, object creation, public signatures, suppressions, and complexity.
- Decide whether graph analysis, package-boundary analysis, local rules, or design-pattern rules need to run.
- Maintain dependency/dependent maps for blast-radius calculation.

Defence explanation:

> `ImpactAnalyzer` is the key reason RICA does not have to re-run every detector after every small edit. It is the incremental revalidation brain.

### `src/fileWatcher.ts`

This file listens for Java file changes in VS Code.

Main responsibilities:

- Debounce frequent edits so RICA does not run too often while typing.
- Mark files dirty so old diagnostics disappear quickly.
- Trigger parsing/analysis on save.
- Handle created, changed, deleted, and renamed Java files.

Defence explanation:

> `FileWatcher` connects editor events to incremental analysis. It improves user experience because warnings update after edits instead of waiting for a manual full scan.

## 6. Violation Model and Documentation

### `src/domain/violations.ts`

Defines the unified violation model used by the UI and diagnostics.

Important types:

- `ViolationSeverity`
- `FixSafety`
- `RemediationSuggestion`
- `DiagnosticRange`
- `RelatedInformation`
- `ViolationContextMetadata`
- `ViolationConfidence`
- `ViolationAnalysisMetadata`
- `Violation`
- `ViolationSummary`

Defence explanation:

> This file is important because all detector outputs eventually become one common `Violation` shape. That is why the panel, diagnostics, docs, tests, and AI advisory can all understand the same result object.

### `src/violationCatalog.ts`

Purpose: central catalogue of all RICA rules and documentation metadata.

It contains:

- Rule codes such as `RICA-V101`, `RICA-V303`, `RICA-V501`.
- Rule titles.
- Severity and category metadata.
- Trigger descriptions.
- Mitigation hints.
- Documentation content used by `scripts/generate-docs.cjs`.

Defence explanation:

> `violationCatalog.ts` prevents drift between detectors and documentation. If a rule has a code, it should have catalogue metadata and generated docs.

### `src/fixSuggestionEngine.ts`

Purpose: attaches remediation suggestions to violations.

Important responsibilities:

- Decide whether a finding can have a safe/simple suggestion.
- Add manual design guidance when automatic fixing would be unsafe.
- Keep architecture-heavy fixes as guidance rather than blindly editing user code.

Defence explanation:

> RICA does not claim to automatically fix every architecture problem. The fix suggestion engine attaches guidance, while complex refactors remain developer-reviewed.

### `src/documentation.ts`

Purpose: opens bundled RICA documentation inside VS Code.

### `src/documentationCodeActionProvider.ts`

Purpose: adds a lightbulb action so developers can open the matching RICA documentation page from a diagnostic.

### `src/codeActionProvider.ts`

Purpose: provides VS Code quick-fix/code-action integration.

Important responsibilities:

- Inspect active RICA violations.
- Show available quick-fix/guidance actions.
- Avoid unsafe automatic edits for complex architecture fixes.

## 12. Domain Type Files

### `src/domain/astTypes.ts`

## 15. How A Violation Is Created

Example: controller directly performs an HTTP call.

1. `JavaParser` extracts object creation or method call facts such as `new RestTemplate()` or `webClient.post()`.
2. `ControllerLayerAnalyzer.analyze()` sees the class is a controller.
3. It recognises the HTTP client type from its known pattern list.
4. It creates a `ControllerLayerViolation`.
5. `ViolationManager.layerViolationToUnified()` maps the legacy type to a RICA code such as `RICA-V110`.
6. `FixSuggestionEngine` adds remediation guidance.
7. `VscodeDiagnosticReporter` shows an underline.
8. `ViolationsWebviewPanel` shows the row in the panel.
9. `documentationCodeActionProvider` lets the user open the rule page.

## 16. How Incremental Revalidation Works

Example: user edits one Java file.

1. `FileWatcher` receives a save event.
2. `ViolationManager.onFileSaved()` parses the changed file.
3. `ImpactAnalyzer.diffAstFacts()` compares old AST facts with new AST facts.
4. If imports changed, graph/package rules may run.
5. If method calls changed, local and graph rules may run.
6. If object creation changed, selected design-pattern rules may run.
7. If annotations changed, package-boundary and affected dependent files may run.
8. Old violations for affected areas are removed.
9. New violations are merged.
10. Diagnostics refresh.

This is why the report says RICA uses incremental revalidation rather than blindly rescanning everything on every ordinary edit.

## 17. What To Say In Defence

### If asked "Where is the VS Code extension implemented?"

Answer:

> The entry point is `src/extension.ts`. It registers commands, creates the parser and managers, starts the file watcher, reports diagnostics, opens webviews, and wires optional AI support.

### If asked "Where is the parser?"

Answer:

> The parser is mainly `src/infrastructure/javaParser.ts`. It uses Java parsing output to extract classes, methods, fields, imports, annotations, calls, object creation, complexity metrics, and layer classification facts.

### If asked "Where are violations coordinated?"

Answer:

> `src/violationManager.ts` coordinates all detector modules, maintains the AST cache, builds the graph, runs incremental updates, filters/suppresses violations, adds fix suggestions, and refreshes diagnostics.

### If asked "Where are architecture rules?"

Answer:

> Local layer rules are in `serviceLayerDetector.ts`, `controllerLayerDetector.ts`, `entityLayerDetector.ts`, and `apiResourceLayerDetector.ts`. Cross-file architecture rules are in `crossFileAnalyzer.ts` and `dependencyGraph.ts`. Package boundary rules are in `packageBoundaryDetector.ts`.

### If asked "Where are design-pattern rules?"

Answer:

> They are in `src/designPatternAnalyzer.ts`. It contains deterministic checks for the RICA-V301 to RICA-V323 rule family.

### If asked "Where is AI?"

Answer:

> AI support is in `src/application/ai` and `src/infrastructure/ai`. It is advisory only. The deterministic detector results are produced first, then AI can explain or suggest remediation using structured context.

### If asked "Where are tests?"

Answer:

> Tests are in `src/test`. Mocha runs `src/test/**/*.test.js`. Java fixture files under `src/test/fixtures` are controlled examples used as analyzer input.

## 18. What You Should Personally Understand First

If you do not have time to memorise everything, understand these files in this order:

1. `src/extension.ts`: how VS Code starts RICA.
2. `src/violationManager.ts`: how all analysis is coordinated.
3. `src/infrastructure/javaParser.ts`: how Java code becomes AST facts.
4. `src/controllerLayerDetector.ts`: easiest detector to explain with examples.
5. `src/dependencyGraph.ts`: how project-level dependencies are represented.
6. `src/impactAnalyzer.ts`: how incremental revalidation works.
7. `src/designPatternAnalyzer.ts`: how design-pattern detections are implemented.
8. `src/test/designPattern.test.js`: how design-pattern claims are tested.
9. `src/test/violationManagerIncremental.test.js`: how incremental claims are tested.

## 19. Important Limitation To Say Honestly

Do not say:

> RICA understands every Java program perfectly.

Say:

> RICA extracts practical AST and dependency facts for editor-time architecture analysis. It is deterministic, tested against controlled fixtures, configurable, and explainable, but it does not replace a full Java compiler, complete semantic type resolver, or IFDS data-flow solver.

That answer matches the implementation and the final report.
